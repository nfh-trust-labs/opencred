Onboarding, in plain language

A normal issuer doesn't know what did:web, did.json, or DeDi are — and shouldn't have to. The setup should ask about their situation and make the protocol choices for them.

Proposal · OpenCred desktop · mockup only, no code changed

Four principles

1 · Situation, not protocol

Ask “do you have a website?”, never “did:web or did:key?”. The technical term hides behind an optional “?”.

2 · Safe default, advanced opt-in

The simplest fitting option is pre-selected. Self-hosting and bring-your-own DeDi live under “Advanced”. There is no managed/shared directory — DeDi is the issuer's own.

3 · Keys are invisible

No “keypair” talk. Just: “your key is ready, and it never leaves this device.”

4 · Defer the hard parts

Revocation, schemas, custom DeDi instances → Advanced/Settings, surfaced only when needed. (The public-directory anchor is the deliberate exception — a DeDi issuer publishes during onboarding.)
