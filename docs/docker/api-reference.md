# Docker API Reference

> **Source of truth.** This page documents the `/v1` HTTP surface served by the OpenCred Docker image. It is generated by reading the Hono route handlers in `apps/server/src/routes/*.ts`, the Zod request schemas in those same files, the config schema in `apps/server/src/config.ts`, and the `OpenCredError` hierarchy in `packages/shared/src/errors.ts`. If a curl example or schema in this document ever drifts from the code, the code wins — open a docs PR to fix the drift.
>
> **Legacy contract.** A pre-`/v1` reference still lives at [`docs/self-hosted/api-reference.md`](../self-hosted/api-reference.md). Treat that document as superseded for new integrations: the canonical surface is `/v1` and is documented here. The unprefixed routes (`/health`, `/credentials/issue`, ...) are mounted by the server for backwards compatibility with the desktop main process and pre-`/v1` tests, but they are not the integration target for new clients.

## Overview

The OpenCred Docker image is a headless HTTP server that wraps the same `@opencred/crypto`, `@opencred/vc-core`, `@opencred/schema-engine`, `@opencred/signing`, and `@opencred/verification` packages used by the Desktop Client. It exposes credential issuance and verification through a stateless, JSON-over-HTTP API at `/v1`. There is no persistent server-side session: every issue and verify call is a pure request/response with no record retained after the response is written. The server is built from `apps/server/Dockerfile` and runs `apps/server/dist/index.js` as the non-root `node` user.

## Base URL

```
http://localhost:${OPENCRED_PORT}
```

The default port is `3100` (`apps/server/src/config.ts` — `OPENCRED_PORT.default(3100)`). The container ships HTTP-only on purpose. **Production deployments must sit behind a reverse proxy** (nginx, Caddy, an L7 load balancer, or a service mesh) that terminates TLS, manages certificate rotation, and forwards requests to the OpenCred container. See the reverse-proxy section in [Deployment](deployment.md#reverse-proxy).

## Authentication

OpenCred Server's API is a **signing oracle**: anyone who can reach `POST /v1/credentials/issue` can mint credentials signed by the configured key. Authentication is therefore **fail-closed by default** — the server refuses to start unless one of the following is true.

### Auth modes

| Mode | Set this | Behaviour |
|---|---|---|
| **Production (recommended)** | `OPENCRED_API_KEY=<strong-random-token>` | Every protected endpoint requires `Authorization: Bearer <token>`. Constant-time comparison via `node:crypto.timingSafeEqual()` prevents timing attacks. |
| **Local development opt-out** | `OPENCRED_DEV_MODE_NO_AUTH=true` | Protected endpoints are reachable without an `Authorization` header. The server logs a loud warning at startup. **Refused** if `NODE_ENV=production` is also set. |
| **Misconfigured** | Neither of the above | Server **refuses to start** with a `CONFIG_ERROR`. |

This is enforced in `loadConfig()` (`apps/server/src/config.ts`):

```text
[opencred-server] FATAL: OPENCRED_API_KEY is required. Set OPENCRED_API_KEY
to a strong, randomly generated bearer token before starting the server.
For local development only, you may instead set OPENCRED_DEV_MODE_NO_AUTH=true
to disable authentication; this is REFUSED when NODE_ENV=production.
```

Generate a token with:

```bash
openssl rand -base64 32
# or
node -e 'console.log(require("crypto").randomBytes(32).toString("base64"))'
```

### Public paths

The following paths are always reachable **without** an `Authorization` header so that container orchestrators can probe liveness without holding the API key:

* `GET /health`
* `GET /v1/health`

Every other path under `/v1` is protected.

### NODE_ENV refusal

If `OPENCRED_DEV_MODE_NO_AUTH=true` is set together with `NODE_ENV=production`, the server exits at startup with a `CONFIG_ERROR`. This is a defense-in-depth check: even if the dev-mode flag leaks into a production environment via a stale `.env` file or a misconfigured orchestrator, the server still refuses to run as an unauthenticated signing oracle.

### Auth example

```bash
export OPENCRED_API_KEY="$(openssl rand -base64 32)"

curl -s http://localhost:3100/v1/keys \
  -H "Authorization: Bearer $OPENCRED_API_KEY"
```

A missing or malformed header returns `401 AUTHENTICATION_ERROR`. See [Environment variables](#environment-variables) for the full list of related config values.

## Environment variables

All configuration is loaded from environment variables at startup and parsed by Zod (`apps/server/src/config.ts`). Invalid values cause an immediate exit with a descriptive error. None of these values are ever logged.

| Variable | Required | Default | Description | Example |
|---|---|---|---|---|
| `OPENCRED_API_KEY` | Yes (unless dev mode) | — | Bearer token for protected endpoints. Server refuses to start if both this and `OPENCRED_DEV_MODE_NO_AUTH` are unset. | `sk_prod_8WxR2K9...` |
| `OPENCRED_DEV_MODE_NO_AUTH` | No | `false` | Explicit opt-out from authentication. Local development only. **Refused** when `NODE_ENV=production`. Loud warning emitted at startup. | `true` |
| `NODE_ENV` | No | _(unset)_ | If `production`, the server refuses to start when `OPENCRED_DEV_MODE_NO_AUTH=true`. Defense in depth. | `production` |
| `OPENCRED_PORT` | No | `3100` | TCP port the HTTP server listens on. Range: 1–65535. | `3100` |
| `OPENCRED_LOG_LEVEL` | No | `info` | Pino log level. One of `fatal`, `error`, `warn`, `info`, `debug`, `trace`. | `info` |
| `OPENCRED_KEY_PATH` | No[^1] | _(unset)_ | Absolute path to the signing key file. Supported formats: PEM, JWK, PKCS#8 DER, PFX. Mount as a read-only volume — never bake key material into the image. | `/run/secrets/issuer.pem` |
| `OPENCRED_KEY_PASSWORD` | No | _(unset)_ | Password for PFX/P12 key files. | `changeit` |
| `OPENCRED_KEY_LABEL` | No | `server-key` | Display label shown in `GET /v1/keys` responses. | `prod-issuer` |
| `OPENCRED_SESSION_TTL` | No | `14400` | Ephemeral session TTL in seconds. Default is 4 hours, matching [security invariant 3](../security/invariants.md#3-session-data-is-ephemeral). Minimum 60. | `14400` |
| `OPENCRED_BATCH_ROW_LIMIT` | No | `1000` | Max rows allowed in a single batch CSV. Minimum 1. | `1000` |
| `CSCA_TRUST_STORE_PATH` | No[^2] | _(unset)_ | Absolute path to a directory of PEM-encoded CSCA root certificates used as trust anchors when verifying credentials with embedded `x5c` chains. Required only for DSC-backed credentials. | `/app/trust-store/` |
| `OPENCRED_KMS_PROVIDER` | No | `none` | Cloud KMS provider. One of `aws`, `azure`, `gcp`, `none`. See [`docs/self-hosted/cloud-hsm.md`](../self-hosted/cloud-hsm.md) for IAM/auth requirements per provider. | `aws` |
| `OPENCRED_KMS_KEY_ARN` | When `OPENCRED_KMS_PROVIDER=aws` | _(unset)_ | AWS KMS key ARN. | `arn:aws:kms:us-east-1:...` |
| `OPENCRED_AZURE_KEY_VAULT_URL` | When `OPENCRED_KMS_PROVIDER=azure` | _(unset)_ | Azure Key Vault base URL. | `https://vault.vault.azure.net/` |
| `OPENCRED_AZURE_KEY_NAME` | When `OPENCRED_KMS_PROVIDER=azure` | _(unset)_ | Azure Key Vault key name. | `opencred-issuer` |
| `OPENCRED_GCP_KMS_KEY_NAME` | When `OPENCRED_KMS_PROVIDER=gcp` | _(unset)_ | GCP KMS key resource name including version. | `projects/p/locations/.../cryptoKeyVersions/1` |

[^1]: A signing key is required for `POST /v1/credentials/issue` to succeed. If neither `OPENCRED_KEY_PATH` nor a Cloud HSM provider is configured, the server still starts and `/v1/health` reports `signingKeyLoaded: false`, but every issue request returns `500 INTERNAL_ERROR` (the sanitized fallback for the unhandled `requireSigner()` throw — see [Observability → Health Checks](observability.md#health-checks)).
[^2]: `CSCA_TRUST_STORE_PATH` is only required to verify credentials that carry an `x5c` certificate chain (DSC-backed credentials). Verification of DID-keyed credentials does not need it. When unset, the verifier still functions but fails closed for any credential whose proof carries an `x5c` chain — see [`POST /v1/credentials/verify`](#post-v1credentialsverify) below.

> **Cloud HSM providers.** The `OPENCRED_KMS_*` variables are fully implemented. The factory in `apps/server/src/signing/cloud-hsm/` creates a Signer backed by the configured provider (AWS KMS, Azure Key Vault, or GCP Cloud KMS). Supported key types include ECDSA (P-256, P-384) and RSA (2048, 3072, 4096). See [`docs/self-hosted/cloud-hsm.md`](../self-hosted/cloud-hsm.md) for IAM permissions and key requirements per provider.

## Endpoints

Every endpoint below is mounted under both `/v1/...` (canonical) and `/...` (legacy, kept for the desktop main process and pre-`/v1` tests). New consumers should target `/v1`. Authentication rules apply to both prefixes.

### `GET /v1/health`

Liveness probe for orchestrators and container health checks. Always public — no `Authorization` header required.

**Auth:** none.
**Request body:** none.

**Response: `200 OK`**

```json
{
  "status": "ok",
  "signingKeyLoaded": true,
  "timestamp": "2026-04-08T10:00:00.000Z"
}
```

| Field | Type | Description |
|---|---|---|
| `status` | `string` | Always `"ok"` if the process is running. |
| `signingKeyLoaded` | `boolean` | `true` if a signer was successfully loaded at startup. If `false`, issue endpoints return `500 INTERNAL_ERROR` (the sanitized fallback for the `requireSigner()` throw — see [Observability](observability.md#health-checks)). |
| `timestamp` | `string` | Current ISO-8601 timestamp from the server clock. |

**Example**

```bash
curl -s http://localhost:3100/v1/health
```

```json
{
  "status": "ok",
  "signingKeyLoaded": true,
  "timestamp": "2026-04-08T10:00:00.000Z"
}
```

If `signingKeyLoaded` is `false`, treat it as a critical alert in production: the server is up but cannot issue credentials. Either `OPENCRED_KEY_PATH` is unset, the file is unreadable, or the configured Cloud HSM provider failed to initialise.

### `GET /v1/keys`

Returns metadata about the configured signing key sources. **Never** returns private key material, raw public key bytes, or filesystem paths.

**Auth:** required (unless `OPENCRED_DEV_MODE_NO_AUTH=true`).
**Request body:** none.

**Response: `200 OK`**

When a signer is configured:

```json
{
  "keys": [
    {
      "id": "did:key:zDnaerDaTF5BXEavCrfRZEk316dpbLsfPDZ3WJ5hRTPFU2169",
      "fingerprint": "d6f4e2c9b7a8...e1f0",
      "algorithm": "P-256",
      "type": "software",
      "hasCertificateChain": false,
      "label": "prod-issuer",
      "source": "software-file"
    }
  ]
}
```

| Field | Type | Description |
|---|---|---|
| `keys` | `array` | List of configured signers. The current scaffold supports a single active signer, so this array always has length 0 or 1. |
| `keys[].id` | `string` | The verification method DID identifier. Typically a `did:key` or `did:jwk` URI. |
| `keys[].fingerprint` | `string` | Hex-encoded SHA-256 fingerprint of the public key. |
| `keys[].algorithm` | `string` | Signing algorithm. One of `P-256`, `P-384`, `Ed25519`, `RSA-2048`, `RSA-3072`, `RSA-4096`. |
| `keys[].type` | `string` | Where the key lives. One of `software`, `pkcs11`, `os-cert`. The Docker image supports `software` (file-backed) and `pkcs11` (hardware token via a mounted PKCS#11 library — see [Deployment → Key sources](deployment.md#key-sources)); `os-cert` is Desktop-only. |
| `keys[].hasCertificateChain` | `boolean` | `true` if the key has a bound X.509 certificate chain (e.g. from a PFX import). |
| `keys[].label` | `string` _(optional)_ | Human-readable label set via `OPENCRED_KEY_LABEL`. |
| `keys[].source` | `string` | The configured backend. One of `software-file`, `aws-kms`, `azure-kv`, `gcp-kms`. |

When no signer is configured:

```json
{
  "keys": [],
  "message": "No signing key configured. Set OPENCRED_KEY_PATH or a Cloud HSM provider."
}
```

**Example**

```bash
curl -s http://localhost:3100/v1/keys \
  -H "Authorization: Bearer $OPENCRED_API_KEY"
```

The response body is guaranteed by `apps/server/src/__tests__/v1-smoke.test.ts` to never contain `PRIVATE KEY`, `BEGIN`, `END`, or a JWK `d` field.

### `POST /v1/credentials/issue`

Builds, validates, and signs a Verifiable Credential. The server holds the issuer's private key in memory (loaded once at startup); the request body provides only the public credential payload.

**Auth:** required.
**Content-Type:** `application/json`.

**Request body**

The request is parsed by `issueRequestSchema` in `apps/server/src/routes/credentials.ts`:

```ts
{
  schemaId: string;
  issuerDid: string;
  credentialSubject: Record<string, unknown>;
  validFrom: string;
  validUntil?: string;
  proofFormat?: "vc-jwt" | "data-integrity" | "sd-jwt-vc";  // default "vc-jwt"
  additionalTypes?: string[];
  subjectDid?: string;
  selectiveDisclosureClaims?: string[];
  revocationRegistryUrl?: string;  // must be a valid URL
  credentialSchemaUrl?: string;    // must be a valid URL
  packageFormats?: Array<"qr-png" | "qr-svg" | "pdf" | "json-ld" | "json-compact">;
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `schemaId` | `string` | Yes | Built-in schema id (e.g. `functional-identity/v1`, `electricity/v1`, `open-badges/v3`, `traceability/commercial-invoice/v1`). Use `GET /v1/schemas` to list all available ids. The `credentialSubject` is validated against this schema. |
| `issuerDid` | `string` | Yes | The issuer's DID. Must match the `id` of the active signer (the server uses the active signer regardless, but downstream verifiers will compare these). |
| `credentialSubject` | `object` | Yes | The credential claims. Validated against the JSON Schema bound to `schemaId`. |
| `validFrom` | `string` | Yes | ISO-8601 timestamp marking the start of the credential's validity. |
| `validUntil` | `string` | No | ISO-8601 timestamp for expiry. |
| `proofFormat` | `string` | No (default `vc-jwt`) | Proof format. `data-integrity` is **not** supported with RSA keys (returns `500 CRYPTO_ERROR` — use `vc-jwt` or `sd-jwt-vc` instead). |
| `additionalTypes` | `string[]` | No | Extra `type` values to add to the credential beyond `VerifiableCredential`. |
| `subjectDid` | `string` | No | Subject DID. When set, written to `credentialSubject.id`. |
| `selectiveDisclosureClaims` | `string[]` | No | JSON pointer-style paths into `credentialSubject` whose values become selectively disclosable when `proofFormat=sd-jwt-vc`. |
| `revocationRegistryUrl` | `string` | No | URL of a DeDi status list. When set, the server generates a `urn:uuid:` credential id, computes a SHA-256 revocation hash from the UUID, and adds a `credentialStatus` block of type `dedi`. |
| `credentialSchemaUrl` | `string` | No | URL of an external JSON Schema. When set, written to the credential's `credentialSchema` field with `type: "JsonSchema"`. |
| `packageFormats` | `string[]` | No | Optional packaging formats to render alongside the signed credential. Only applies to JSON credentials, not compact tokens (SD-JWT VC). |

**Security: `rejectKeyMaterial()` defense-in-depth check**

The handler runs `rejectKeyMaterial()` over the entire parsed body **before** any other validation. This is a recursive walk that throws `400 VALIDATION_ERROR` if either of the following is true at any depth in the JSON tree:

1. The body contains a key in the `FORBIDDEN_REQUEST_KEYS` set:
   `privateKey`, `private_key`, `privateKeyJwk`, `private_key_jwk`, `privateKeyPem`, `private_key_pem`, `pkcs8`, `pkcs12`, `pfx`, `p12`, `keyMaterial`, `key_material`.
2. Any string value matches the `PEM_PRIVATE_KEY_RE` regex `/-----BEGIN (?:[A-Z0-9]+ )?PRIVATE KEY-----/`. This covers every PEM private-key header the OpenSSL toolchain produces: PKCS#8 (`BEGIN PRIVATE KEY`), PKCS#8 encrypted (`BEGIN ENCRYPTED PRIVATE KEY`), PKCS#1 RSA (`BEGIN RSA PRIVATE KEY`), SEC1 EC (`BEGIN EC PRIVATE KEY`), OpenSSH (`BEGIN OPENSSH PRIVATE KEY`), and DSA (`BEGIN DSA PRIVATE KEY`). The earlier `"BEGIN PRIVATE KEY"` substring check only caught the PKCS#8 form; the regex closes that gap so key material generated by any openssl default (e.g. `openssl genrsa`, `openssl ecparam -genkey`) is also rejected.

This is in addition to Zod schema parsing — Zod silently drops unknown fields, but this guard generates a loud, audited rejection so misconfigured clients learn fast and never accidentally upload key material. The same check runs on **every** POST route that accepts a JSON body: `/v1/credentials/verify`, `/v1/credentials/batch`, `/v1/credentials/revocation-hash`, `/v1/credentials/revocation-hash/batch`, and `/v1/credentials/package`. The helper is exported from `apps/server/src/routes/credentials.ts` so there is no back-door route that forgets to call it.

**Response: `200 OK`**

For `vc-jwt` and `data-integrity` (JSON credentials):

```json
{
  "credential": {
    "@context": ["https://www.w3.org/ns/credentials/v2"],
    "type": ["VerifiableCredential"],
    "issuer": "did:key:zDnaerDaTF5BXEavCrfRZEk316dpbLsfPDZ3WJ5hRTPFU2169",
    "validFrom": "2025-06-15T00:00:00Z",
    "credentialSubject": {
      "name": "Jane Doe",
      "degree": "Master of Science",
      "institution": "MIT",
      "dateConferred": "2025-06-15"
    },
    "proof": {
      "type": "DataIntegrityProof",
      "cryptosuite": "ecdsa-rdfc-2019",
      "created": "2026-04-08T10:00:00Z",
      "verificationMethod": "did:key:zDnaerDaTF5BXEavCrfRZEk316dpbLsfPDZ3WJ5hRTPFU2169#zDnaerDaTF5BXEavCrfRZEk316dpbLsfPDZ3WJ5hRTPFU2169",
      "proofPurpose": "assertionMethod",
      "proofValue": "z3M..."
    }
  },
  "proofFormat": "data-integrity",
  "isCompactToken": false
}
```

For `sd-jwt-vc` (compact token):

```json
{
  "credential": "eyJhbGciOiJFUzI1NiIsInR5cCI6InZjK3NkLWp3dCJ9.eyJ2Y3QiOiJlZHVjYXRpb24iLC...~WyJzYWx0IiwibmFtZSIsIkphbmUgRG9lIl0~",
  "proofFormat": "sd-jwt-vc",
  "isCompactToken": true
}
```

| Field | Type | Description |
|---|---|---|
| `credential` | `object` _or_ `string` | The signed credential. An object for `vc-jwt` and `data-integrity`; a compact string token for `sd-jwt-vc`. |
| `proofFormat` | `string` | Echoes the requested proof format. |
| `isCompactToken` | `boolean` | `true` only when `proofFormat=sd-jwt-vc`. |
| `packagedOutputs` | `array` _(optional)_ | Present only when `packageFormats` was set. Each entry: `{ format, data, mimeType, suggestedFileName, encoding }`. Binary outputs (PDF, PNG) are base64-encoded. |

**Example**

```bash
curl -s http://localhost:3100/v1/credentials/issue \
  -H "Authorization: Bearer $OPENCRED_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "schemaId": "education",
    "issuerDid": "did:key:zDnaerDaTF5BXEavCrfRZEk316dpbLsfPDZ3WJ5hRTPFU2169",
    "credentialSubject": {
      "name": "Jane Doe",
      "degree": "Master of Science",
      "institution": "MIT",
      "dateConferred": "2025-06-15"
    },
    "validFrom": "2025-06-15T00:00:00Z",
    "validUntil": "2030-06-15T00:00:00Z",
    "proofFormat": "data-integrity"
  }'
```

**Error responses**

| Status | Code | When |
|---|---|---|
| `400` | `VALIDATION_ERROR` | The request body failed Zod parsing, contained a forbidden key, or contained a PEM string. The response includes `details[]` for Zod errors. |
| `400` | `SCHEMA_VALIDATION_ERROR` | `credentialSubject` did not satisfy the JSON Schema bound to `schemaId`. The response includes a `validationErrors` array. |
| `401` | `AUTHENTICATION_ERROR` | Missing, malformed, or invalid `Authorization` header. |
| `500` | `CRYPTO_ERROR` | `proofFormat=data-integrity` was requested with an RSA key. Switch to `vc-jwt` or `sd-jwt-vc`. |
| `500` | `INTERNAL_ERROR` | Any unhandled error. The original error is logged but not echoed to the response. |

Example `400 VALIDATION_ERROR` body when a private key field is smuggled in:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request rejected: field \"privateKey\" is forbidden. OpenCred never accepts private key material via the HTTP API."
  }
}
```

Example `400 SCHEMA_VALIDATION_ERROR` body when required fields are missing:

```json
{
  "error": {
    "code": "SCHEMA_VALIDATION_ERROR",
    "message": "Validation failed for schema 'education'",
    "validationErrors": [
      { "instancePath": "", "keyword": "required", "message": "must have required property 'degree'" },
      { "instancePath": "", "keyword": "required", "message": "must have required property 'institution'" }
    ]
  }
}
```

### `POST /v1/credentials/verify`

Verifies a signed Verifiable Credential. Accepts JSON-LD credentials (Data Integrity), compact JWTs (`vc-jwt`), and compact SD-JWT VC tokens — the format is auto-detected.

**Auth:** required.
**Content-Type:** `application/json`.

**Request body**

```ts
{
  credential: string;  // a JSON-stringified VC, a compact JWT, or a compact SD-JWT VC
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `credential` | `string` | Yes | The credential to verify. For Data Integrity credentials, JSON-stringify the credential object before sending. For compact tokens (`vc-jwt`, `sd-jwt-vc`), pass the token directly. |

The same `rejectKeyMaterial()` defense-in-depth guard runs on this endpoint too. Even verify requests must not contain a private key field or PEM string.

**X.509 trust anchors**

Verification uses a composite DID resolver covering `did:key`, `did:jwk`, and `did:web`. For credentials whose proof carries an X.509 certificate chain (`x5c` header in `vc-jwt`, or an embedded chain in a `data-integrity` proof), the verifier additionally invokes `checkX509Chain` from `@opencred/verification`, which requires CSCA root certificates.

> **`CSCA_TRUST_STORE_PATH` requirement.** When the request credential carries an `x5c` chain, the verifier loads CSCA trust anchors from the directory pointed at by `CSCA_TRUST_STORE_PATH` and validates the chain against them. If the env var is unset, **the verifier fails closed for any DSC-backed credential** — verification still completes for DID-keyed credentials but DSC-backed ones return `valid: false` with a check failure. To verify x5c-bearing credentials in production, set `CSCA_TRUST_STORE_PATH` to a directory of PEM-encoded CSCA roots and mount it read-only into the container.

**Response: `200 OK`**

The response body is assembled by `buildVerifyResponseBody()` in `apps/server/src/routes/credentials.ts`, which runs the raw `verifyCredential()` result through `sanitizeChecksForServerResponse()` before serialization. That sanitizer **drops the `detail` field from every check** so the HTTP API never leaks internal state across the network boundary — CSCA trust anchor subject DNs, X.509 parser errors, or filesystem-shaped strings. The desktop IPC handler (trusted local caller) still returns the full shape with `detail`; the server does not. See [CLAUDE.md invariant #5](../security/invariants.md#5-no-secrets-in-error-responses).

```json
{
  "valid": true,
  "code": "VALID",
  "message": "Credential is valid.",
  "checks": [
    { "name": "signature", "passed": true },
    { "name": "date",      "passed": true }
  ]
}
```

A revocation check entry (`{ "name": "revocation", "passed": true }`) is appended when a `DeDiClient` is configured and the credential carries a `credentialStatus`. A Bitstring Status List check is appended when the credential's `credentialStatus.type` is `BitstringStatusListEntry`.

For an invalid credential:

```json
{
  "valid": false,
  "code": "INVALID",
  "message": "Verification failed.",
  "checks": [
    { "name": "signature", "passed": false }
  ]
}
```

| Field | Type | Description |
|---|---|---|
| `valid` | `boolean` | `true` if every check passed. |
| `code` | `string` | Top-level outcome from `@opencred/verification`. One of `VALID`, `REVOKED`, `EXPIRED`, `INVALID`, `UNRESOLVABLE`, `CONTEXT_MISSING`. This is the stable enum for programmatic handling — prefer it over parsing `message`. |
| `message` | `string` | **Hardcoded** human-readable summary. Always exactly `"Credential is valid."` when `valid === true`, always exactly `"Verification failed."` when `valid === false`. The server never echoes a raw `detail` string here. |
| `checks` | `array` | The list of verification checks. Each entry has exactly `name` (string) and `passed` (boolean). **There is no `detail` field** — it is stripped by `sanitizeChecksForServerResponse()` before the response is written. |

> **HTTP 200 even for invalid credentials.** This endpoint returns `200 OK` whenever verification ran to completion, regardless of the outcome. A `valid: false` response is **not** a transport error — it means "verification ran and the credential failed". A `4xx` or `5xx` response means "verification could not run". Clients must inspect `valid` (or `code`) to make a trust decision.

**Example**

```bash
curl -s http://localhost:3100/v1/credentials/verify \
  -H "Authorization: Bearer $OPENCRED_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "credential": "{\"@context\":[\"https://www.w3.org/ns/credentials/v2\"],\"type\":[\"VerifiableCredential\"],\"issuer\":\"did:key:zDnaerDaTF5BXEavCrfRZEk316dpbLsfPDZ3WJ5hRTPFU2169\",\"validFrom\":\"2025-06-15T00:00:00Z\",\"credentialSubject\":{\"name\":\"Jane Doe\",\"degree\":\"Master of Science\",\"institution\":\"MIT\",\"dateConferred\":\"2025-06-15\"},\"proof\":{\"type\":\"DataIntegrityProof\",\"cryptosuite\":\"ecdsa-rdfc-2019\",\"proofValue\":\"z3M...\"}}"
```

```bash
curl -s http://localhost:3100/v1/credentials/verify \
  -H "Authorization: Bearer $OPENCRED_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "credential": "eyJhbGciOiJFUzI1NiIsInR5cCI6InZjK3NkLWp3dCJ9.eyJ2Y3QiOi...~WyJzYWx0IiwibmFtZSIsIkphbmUgRG9lIl0~"
  }'
```

**Error responses**

| Status | Code | When |
|---|---|---|
| `400` | `VALIDATION_ERROR` | Missing `credential` field, request body contained a forbidden key, or contained a PEM string. |
| `400` | `VERIFICATION_ERROR` | The verifier could not parse the credential at all (malformed JSON, invalid JWT structure, unsupported format). |
| `401` | `AUTHENTICATION_ERROR` | Missing, malformed, or invalid `Authorization` header. |
| `500` | `DID_RESOLUTION_ERROR` | A DID could not be resolved (e.g. `did:web` host unreachable, DNS-rebinding rejected, invalid DID document). |
| `500` | `INTERNAL_ERROR` | Any unhandled error. |

### `GET /v1/schemas`

Lists the built-in credential schemas bundled with `@opencred/schema-engine`. The registry includes schemas from multiple sources (OpenCred built-in, DIF, W3C Traceability, Open Badges). `GET /v1/schemas/:id` returns the full JSON Schema for a single id. Schema IDs may contain slashes (e.g. `functional-identity/v1`, `traceability/commercial-invoice/v1`).

**Auth:** required.
**Request body:** none.

**Response: `200 OK`** (list)

```json
{
  "schemas": [
    { "id": "functional-identity/v1", "version": "1.0.0", "contextUrl": "...", "source": {...} },
    { "id": "electricity/v1",         "version": "1.0.0", "contextUrl": "...", "source": {...} },
    { "id": "salary-slip/v1",         "version": "1.0.0", "contextUrl": "...", "source": {...} },
    { "id": "immunization/v1",        "version": "1.0.0", "contextUrl": "...", "source": {...} },
    { "id": "open-badges/v3",         "version": "3.0.0", "contextUrl": "...", "source": {...} }
  ]
}
```

Each entry includes `id`, `version`, `contextUrl` (the JSON-LD context URL), and `source` (provenance metadata). The full list is generated at build time from bundled schemas.

**Response: `200 OK`** (`/v1/schemas/:id`)

```json
{
  "id": "functional-identity/v1",
  "version": "1.0.0",
  "contextUrl": "...",
  "schema": { "$id": "...", "type": "object", "properties": { "...": {} } },
  "source": {...}
}
```

Returns `404 NOT_FOUND` if the id is not in the registry. Source: `apps/server/src/routes/schemas.ts`.

### `POST /v1/credentials/batch`

Starts a batch-issuance job from a CSV payload. Returns a `jobId` immediately and processes the rows in the background.

**Auth:** required.
**Content-Type:** `application/json`.

**Request body**

```ts
{
  csvContent: string;
  schemaId: string;
  issuerDid: string;
  validFrom: string;
  validUntil?: string;
  proofFormat?: "vc-jwt" | "data-integrity" | "sd-jwt-vc";  // default "vc-jwt"
  additionalTypes?: string[];
  revocationRegistryUrl?: string;  // must be a valid URL
  credentialSchemaUrl?: string;    // must be a valid URL
  selectiveDisclosureClaims?: string[];
  columnMapping?: Record<string, string>;
  delimiter?: "," | ";" | "\t";
}
```

The CSV row count is capped at `OPENCRED_BATCH_ROW_LIMIT` (default `1000`); exceeding it returns `400 VALIDATION_ERROR`. `rejectKeyMaterial()` runs on the full request body.

**Response: `202 Accepted`**

```json
{
  "jobId": "a1e7c3f9-4b2d-4f21-8c3a-1f4d7e9b2c01",
  "headers": ["email", "name", "degree"],
  "validCount": 42,
  "invalidCount": 1,
  "totalCount": 43,
  "parseErrors": [
    { "rowIndex": 7, "errors": ["missing field: degree"] }
  ]
}
```

`parseErrors` is omitted when every row parsed cleanly. Source: `apps/server/src/routes/batch.ts`.

### `GET /v1/credentials/batch/:jobId`

Returns live progress for a batch job. Safe to poll.

**Auth:** required.
**Request body:** none.

**Response: `200 OK`**

```json
{
  "jobId": "a1e7c3f9-4b2d-4f21-8c3a-1f4d7e9b2c01",
  "total": 42,
  "completed": 17,
  "successCount": 16,
  "errorCount": 1,
  "skippedCount": 0,
  "running": true,
  "cancelled": false
}
```

Returns `404 NOT_FOUND` if the `jobId` is unknown.

`GET /v1/credentials/batch/:jobId/results` returns the per-row outcomes as `{ jobId, results: [{ rowIndex, status, error?, credential?, isCompactToken? }] }`. If the job is still running, it returns `409 JOB_RUNNING` — poll the progress endpoint until it reports `running: false`. Source: `apps/server/src/routes/batch.ts`.

### `POST /v1/credentials/revocation-hash`

Computes the canonical SHA-256 revocation hash for a single credential using JCS canonicalization, via `computeRevocationHash` in `@opencred/crypto`. Stateless — nothing is persisted.

**Auth:** required.
**Content-Type:** `application/json`.

**Request body**

```ts
{ credential: Record<string, unknown> }
```

**Response: `200 OK`**

```json
{ "hash": "d6f4e2c9b7a8...e1f0" }
```

`rejectKeyMaterial()` runs on the request body. Source: `apps/server/src/routes/revocation.ts`.

Batch version of the above. Computes revocation hashes for an ordered list of credentials.

**Auth:** required.

**Request body**


**Response: `200 OK`**

```json
{
  "hashes": [
    { "index": 0, "hash": "d6f4e2c9b7a8...e1f0" },
```

### `POST /v1/credentials/package`

Packages an already-signed credential into one or more delivery formats (PDF, QR PNG, QR SVG, JSON-LD, compact JSON).

**Auth:** required.
**Content-Type:** `application/json`.

**Request body**

```ts
{
  credential: Record<string, unknown>;
  formats?: Array<"qr-png" | "qr-svg" | "pdf" | "json-ld" | "json-compact">;  // default ["json-ld"]
}
```

**Response: `200 OK`**

```json
{
  "outputs": [
    {
      "format": "pdf",
      "data": "JVBERi0xLjQKJcfs...",
      "mimeType": "application/pdf",
      "suggestedFileName": "credential.pdf",
      "encoding": "base64"
    }
  ],
  "errors": []
}
```

Binary formats (`pdf`, `qr-png`) are base64-encoded with `encoding: "base64"`. Text formats (`qr-svg`, `json-ld`, `json-compact`) are returned inline with `encoding: "utf-8"`. Any per-format packaging failures are reported in `errors` without failing the whole request. `rejectKeyMaterial()` runs on the request body. Source: `apps/server/src/routes/packaging.ts`.

## Error response format

Every error response from the server follows the same JSON envelope, defined by `OpenCredError.toJSON()` in `packages/shared/src/errors.ts`:

```json
{
  "error": {
    "code": "STRING_CODE",
    "message": "Human-readable description"
  }
}
```

`SchemaValidationError` adds a `validationErrors` array:

```json
{
  "error": {
    "code": "SCHEMA_VALIDATION_ERROR",
    "message": "Validation failed for schema 'education'",
    "validationErrors": [ /* AJV error objects */ ]
  }
}
```

Zod parse failures from request body validation use the same envelope and add a `details` array:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed",
    "details": [
      { "path": "validFrom", "message": "Required" }
    ]
  }
}
```

### Common error codes

| Code | HTTP status | Source class | Meaning |
|---|---|---|---|
| `VALIDATION_ERROR` | 400 | `ValidationError`, Zod handler | Request body failed schema parsing or hit the `rejectKeyMaterial` guard. |
| `SCHEMA_VALIDATION_ERROR` | 400 | `SchemaValidationError` | `credentialSubject` did not satisfy the JSON Schema. |
| `VERIFICATION_ERROR` | 400 | `VerificationError` | Verifier could not parse the credential. |
| `DELEGATION_ERROR` | 400 | `DelegationError` | Delegated issuance failed. |
| `AUTHENTICATION_ERROR` | 401 | `AuthenticationError` | Bearer token missing, malformed, or invalid. |
| `AUTHORIZATION_ERROR` | 403 | `AuthorizationError` | Authenticated but not allowed. |
| `NOT_FOUND` | 404 | `NotFoundError`, `notFound()` handler | Endpoint or resource not found. |
| `CONFLICT` | 409 | `ConflictError` | Generic resource state conflict. |
| `JOB_RUNNING` | 409 | batch route handler | Returned by `GET /v1/credentials/batch/:jobId/results` when the batch job is still running. Poll `GET /v1/credentials/batch/:jobId` for progress until it reports `running: false`. |
| `SESSION_EXPIRED` | 410 | `SessionExpiredError` | Ephemeral session payload expired (TTL elapsed). |
| `PAYLOAD_TOO_LARGE` | 413 | `PayloadTooLargeError` | Request body exceeded the configured limit. |
| `RATE_LIMIT_EXCEEDED` | 429 | `RateLimitError` | Client hit a rate limit. |
| `CRYPTO_ERROR` | 500 | `CryptoError` | Signing or proof construction failed (e.g. RSA + `data-integrity`). |
| `DID_RESOLUTION_ERROR` | 500 | `DIDResolutionError` | A DID could not be resolved. |
| `DEDI_CLIENT_ERROR` | 502 | `DeDiClientError` | DeDi registry call failed. |
| `INTERNAL_ERROR` | 500 | unhandled fallback | Any error not in the `OpenCredError` hierarchy. The original error is logged but not echoed. |
| `NOT_IMPLEMENTED` | 501 | `NotImplementedError` | Endpoint stubbed out (e.g. Cloud HSM provider not yet wired). |
| `CONFIG_ERROR` | 500 | `ConfigError` | Surfaced at startup, not from a request. The server exits before serving traffic. |

Unknown errors fall through to a `500 INTERNAL_ERROR` response with the generic message `"An internal error occurred"`. The original `err.message` is logged via pino at `error` level for operators, but never returned to the client. This is enforced by `apps/server/src/middleware/error-handler.ts`.

## Security model

OpenCred Server is built around the [seven security invariants](../security/invariants.md). The four most relevant to API consumers are:

1. **The API never accepts private key material.** No endpoint, no field. Enforced by both Zod schemas (which never declare a private-key field) and `rejectKeyMaterial()` (which recursively rejects forbidden keys and PEM strings). See [security invariant 1](../security/invariants.md#1-never-touch-issuer-private-keys).
2. **Authentication is fail-closed.** The server refuses to start without an explicit auth decision. There is no silent fallback. See [Authentication](#authentication) above.
3. **Logs never contain key material.** Pino logs only the key id, fingerprint, algorithm, and source. Request bodies for `/credentials/issue` are **not** logged because they may carry credential-subject PII. See [Observability — what is and is not logged](observability.md#what-is-and-is-not-logged) and [security invariant 2](../security/invariants.md#2-never-log-key-material).
4. **Error responses are sanitized.** All errors flow through the `OpenCredError` hierarchy, which guarantees a consistent JSON shape with no key material, file paths, or internal stack traces. Unknown errors are mapped to a generic `INTERNAL_ERROR`. See [security invariant 5](../security/invariants.md#5-no-secrets-in-error-responses).

For the full model, see [`docs/security/README.md`](../security/README.md).
